Local-First Architectures (Revised)

Three ways to build a local web tool that integrates directly with Screaming Frog CLI

A

Python Local Server

FastAPI backend running on localhost. Shells out to SF CLI for crawl/exports. Uses google-api-python-client for GSC, BeautifulSoup for page fetching. React or vanilla JS frontend.

Pros

  • SF MCP is Python — borrow patterns
  • google-api-python-client is official, mature
  • pandas for CSV/analytics
  • subprocess management is straightforward

Cons

  • Python packaging can be fiddly
  • Two languages if using React frontend
B

Node.js Local Server

Express or Next.js on localhost. child_process for SF CLI. Google APIs Node.js client for GSC. Cheerio/Puppeteer for page parsing. TypeScript throughout.

Pros

  • Single language (TypeScript)
  • Excellent for real-time dashboards
  • Next.js gives SSR + API routes

Cons

  • Google Node.js client less mature than Python version
  • CSV processing less ergonomic than pandas
  • SF CLI subprocess management in Node
C

Electron Desktop App

Full desktop app via Electron. Bundles Python backend. Native OS integration — file dialogs, system tray, auto-launch. Polished installation experience.

Pros

  • Native OS experience
  • No "open localhost:3000" friction
  • Bundled dependencies — no pip install

Cons

  • Heavy (~150MB+ bundle)
  • Complex build/packaging
  • Overkill for a table dashboard

My Recommendation: Approach A — Python Local Server

Python is the natural choice here. The Screaming Frog MCP server is already Python — we can study its CLI integration patterns. google-api-python-client is Google's official library with excellent GSC support. pandas makes CSV processing trivial. And subprocess management for the SF CLI is straightforward. For the frontend, we can keep it simple with a lightweight framework (HTMX or vanilla JS) or go with React — both work with FastAPI serving the static files. The whole thing runs with a single pip install and python app.py.
