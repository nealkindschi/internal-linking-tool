Choose an Architecture

Three ways to build the Internal Linking Tool — each with different strengths

A

Next.js Full-Stack

Single codebase for frontend + backend. API routes handle GSC OAuth, CSV parsing, and page fetching. Server components for the dashboard. Deploy to Vercel.

Pros

  • One language (TypeScript)
  • Simplest deployment
  • Great for real-time dashboards

Cons

  • Page fetching is IO-heavy — could block API routes
  • Less mature for CSV/analytics than Python
B

Python Backend + React Frontend

FastAPI backend for data processing (CSV parsing, GSC API, page fetching, matching). React frontend for the dashboard. Separate services, more powerful analytics.

Pros

  • Python excels at CSV/analytics
  • google-api-python-client is official
  • Async HTTP fetching (httpx/aiohttp)

Cons

  • Two codebases to maintain
  • More complex deployment
  • Requires API contract between front/back
C

Lightweight SPA + Proxy

React/Vue SPA that does CSV parsing client-side. A thin Node/Python proxy handles GSC OAuth (to protect secrets). Page fetching via browser — limited by CORS.

Pros

  • Minimal backend infrastructure
  • Fast to prototype
  • Static hosting possible

Cons

  • CORS limits page fetching
  • Large CSVs choke the browser
  • GSC token management is fragile

My Recommendation: Approach A — Next.js

For a single-URL tool with a dashboard UI, Next.js gives you the fastest path to a working product. API routes handle the heavy lifting server-side (no CORS issues), server components render tables efficiently, and deployment is one command. If the CSV analytics become a bottleneck later, you can always extract that logic into a Python microservice without changing the frontend.
